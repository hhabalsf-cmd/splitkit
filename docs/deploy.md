# Deploying to AWS

```
viewer ──HTTPS──▶ CloudFront ──HTTP + secret header──▶ ALB ──▶ ECS Fargate task ──TLS──▶ RDS Postgres 16
                  (*.cloudfront.net cert)              (CloudFront IPs only)   (public subnet,      (private subnet,
                                                                               inbound from ALB)    inbound from task)
GitHub Actions ──OIDC──▶ deploy role ──▶ ECR push + ECS rolling deploy (circuit breaker rollback)
```

Known trade-off: without a custom domain there is no ACM certificate for the ALB, so the
CloudFront→ALB hop is plain HTTP inside AWS's network (viewer→CloudFront is HTTPS). Adding a
domain + ACM cert and switching the origin to `https-only` closes that.

All of it is Terraform in `infra/terraform/`. Secrets (DB DSN, admin key) are generated by
Terraform, stored in Secrets Manager and injected into the task; GitHub holds no AWS keys.

## Cost (us-west-2, on-demand, always on)

| Item | ~USD/month |
|---|---|
| ALB (hourly + minimal LCU) | 17 |
| Public IPv4: 2 for the ALB, 1 for the task | 11 |
| RDS db.t4g.micro + 20 GiB gp3 | 14 |
| Fargate 0.25 vCPU / 1 GiB | 11 |
| Secrets Manager, CloudWatch Logs, ECR, CloudFront | ~2 |
| **Total** | **~55** |

Design choices that keep it there: no NAT gateway (saves ~$32), single-AZ RDS, Container
Insights off, 14-day log retention. `use_fargate_spot = true` cuts compute to ~$3 at the risk of
brief interruptions. `terraform destroy` returns the bill to ~$0 (a final DB snapshot is kept
unless `db_final_snapshot = false`).

## First deploy

Prereqs: `aws configure` with an admin-capable profile, Docker running.

```bash
# 1. remote-state bucket (once per account)
terraform -chdir=infra/terraform/bootstrap init
terraform -chdir=infra/terraform/bootstrap apply
terraform -chdir=infra/terraform/bootstrap output -raw backend_config > infra/terraform/backend.hcl

# 2. registry, then an initial image so the service has something to run
terraform -chdir=infra/terraform init -backend-config=backend.hcl
terraform -chdir=infra/terraform apply -target=aws_ecr_repository.app
scripts/deploy/push_bootstrap_image.sh

# 3. everything else (RDS takes ~5-10 min, CloudFront ~5 min)
terraform -chdir=infra/terraform apply

# 4. wire CI (repository variables, not secrets; none of these are sensitive)
gh variable set AWS_DEPLOY_ROLE_ARN --body "$(terraform -chdir=infra/terraform output -raw github_deploy_role_arn)"
gh variable set AWS_REGION --body us-west-2
gh variable set SPLITKIT_URL --body "$(terraform -chdir=infra/terraform output -raw app_url)"
```

From then on every push to `main` builds the image, pushes `splitkit:<sha>`, registers a new task
definition revision and waits for the service to stabilise, then hits `/health` through CloudFront.

## Operating

```bash
# admin key for creating experiments
aws secretsmanager get-secret-value --secret-id splitkit/admin-key --query SecretString --output text

# logs
aws logs tail /ecs/splitkit --follow

# allow a site's browser SDK calls (CORS), then redeploy to pick it up
terraform -chdir=infra/terraform apply -var='cors_origins=["https://example.vercel.app"]'
gh workflow run CI --ref main
```

Terraform owns the task definition's shape (env, secrets, CPU/memory); CI owns the image. CI
always starts from the latest revision, so Terraform changes ship on the next deploy.

## Tear down

```bash
terraform -chdir=infra/terraform destroy
gh variable delete AWS_DEPLOY_ROLE_ARN   # deploy job skips itself again
```
